API 0xSeq (0xEscrow)

0xSeq est un service de paiement sous séquestre (escrow) automatisé, sécurisé et interopérable, propulsé par Django REST Framework et connecté au processeur de paiement GeniusPay (Mobile Money & Cartes bancaires).

1. Vue d'ensemble

L'objectif de 0xSeq est d'offrir une garantie mutuelle lors des transactions en ligne : l'acheteur consigne ses fonds dans un compte sécurisé (séquestre) et le vendeur expédie le produit ou service avec la certitude que l'argent est disponible. Une fois la prestation vérifiée et validée, les fonds sont libérés vers le vendeur.

Points clés de l'architecture :

  • Contrôle d'accès strict : Gestion des rôles différenciés (Acheteur, Vendeur, Développeur, Administrateur).
  • Machine à états financière : Transitions d'états vérifiées et protégées contre les fraudes et doubles dépenses.
  • Intégration GeniusPay en temps réel : Écoute des webhooks signés cryptographiquement en HMAC SHA-256.
  • Écosystème Développeur : Clés API sécurisées par hachage SHA-256 et authentification JWT isolée.

2. Cycle de Vie d'un Séquestre

Chaque paiement sous séquestre transite selon un automate d'états immuable :

CREATED (Initié) ➔ BLOCKED (Fonds sous séquestre) ➔ RELEASED (Libéré au vendeur)

ou BLOCKED ➔ REFUNDED (Remboursé à l'acheteur) en cas de litige résolu par un administrateur.

Statut Description Action déclenchante
CREATED Transaction initialisée par le client, en attente de versement. POST /api/payments/
BLOCKED Fonds déposés et gelés sur le compte séquestre de GeniusPay. Webhook GeniusPay payment.success
RELEASED Prestation validée, argent transféré au vendeur. POST /api/payments/{id}/release/
REFUNDED Commande annulée ou litige résolu, fonds renvoyés au client. POST /api/payments/{id}/refund/ (Admin)

3. Rôles & Permissions

Le modèle utilisateur gère les types de profils suivants :

  • client : Acheteur pouvant initier des paiements et libérer les fonds après livraison.
  • seller : Vendeur pouvant être désigné comme bénéficiaire d'une transaction.
  • developer : Développeur intégrant l'API 0xSeq, habilité à gérer ses clés d'API.
  • deaph : Administrateur système disposant des droits de litige et de remboursement.

4. Authentification Clients & Vendeurs

L'authentification s'effectue via des jetons JWT (JSON Web Tokens) avec l'en-tête standard Authorization: Bearer <access_token>.

Méthode Route Description
POST /api/register/ Création d'un compte client ou vendeur (rôle standard).
POST /api/token/ Obtention d'une paire de jetons (access + refresh).
POST /api/token/refresh/ Renouvellement d'un token d'accès expiré. 
# Connexion client
curl -X POST http://127.0.0.1:8000/api/token/ \
  -H "Content-Type: application/json" \
  -d '{"username": "mon_client", "password": "mon_mot_de_passe"}'

5. Espace Développeurs (Page Dédiée)

Les développeurs disposent d'un portail et d'un flux d'authentification dédiés. Tout utilisateur standard (client ou vendeur) tentant de s'authentifier sur le portail développeur verra sa requête rejetée.

Méthode Route Description
POST /api/developer/register/ Inscription développeur (attribue automatiquement le rôle developer).
POST /api/developer/token/ Connexion JWT réservée aux comptes développeurs.
Sécurité Espace Développeur : L'endpoint /api/developer/token/ valide automatiquement le rôle utilisateur en base. Si un compte client tente d'y accéder, l'API renvoie un code 400 Bad Request avec le motif : « Accès refusé : Ce compte n'est pas un compte développeur. »

6. Endpoints des Paiements

Méthode Route Accès Description
GET /api/payments/ Authentifié Liste des transactions impliquant l'utilisateur connecté.
POST /api/payments/ Client Initialisation d'un séquestre vers un vendeur.
GET /api/payments/{id}/ Parties prenantes Détails complets d'un paiement sous séquestre.
POST /api/payments/{id}/release/ Acheteur Déblocage des fonds vers le vendeur (statut RELEASED).
POST /api/payments/{id}/refund/ Admin Remboursement de l'acheteur en cas de litige (statut REFUNDED).

Exemple : Créer un séquestre en FCFA (XOF)

Pour une transaction de 25 000 FCFA, 0xSeq retient automatiquement 1% de commission (250 FCFA) et le montant net alloué au vendeur est de 24 750 FCFA.

curl -X POST http://127.0.0.1:8000/api/payments/ \
  -H "Authorization: Bearer VOTRE_JWT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "seller": 2,
    "amount": "25000.00"
  }'

7. Webhooks GeniusPay

Le backend 0xSeq écoute les notifications instantanées émises par GeniusPay sur l'endpoint public suivant :

POST /api/webhooks/geniuspay/

Événements écoutés :

  • payment.success : Le client a réglé. Les fonds passent en BLOCKED.
  • cashout.completed : Le virement vers le vendeur a réussi. Le séquestre passe en RELEASED.
  • payment.refunded : Remboursement confirmé par GeniusPay. Statut REFUNDED.
Contrôle d'intégrité HMAC SHA-256 : Chaque requête webhook envoyée par GeniusPay doit inclure l'en-tête X-GeniusPay-Signature calculé à partir de la variable GENIUS_PAY_WEBHOOK_SECRET. Toute requête non authentique est automatiquement bloquée.

8. Clés d'API & En-tête X-API-Key

Les développeurs connectés peuvent générer des identifiants d'API permanents afin d'intégrer 0xSeq directement dans leurs plateformes e-commerce ou applications tierces.

Authentification sans JWT : Les requêtes d'API externes peuvent être authentifiées directement avec l'en-tête HTTP :
X-API-Key: 0xs_live_xxxxxxxxxxxxxxxxxxxxxxxx
Méthode Route Description
GET /api/keys/ Liste des clés de l'application (le secret est masqué).
POST /api/keys/ Génération d'une nouvelle clé. Le secret en clair n'est retourné qu'une seule fois.
DELETE /api/keys/{id}/revoke/ Révocation immédiate d'une clé compromise.

9. Litiges & Vérification d'Identité (KYC)

Gestion des Litiges (Disputes)

En cas de problème sur une transaction (colis non livré, produit endommagé), l'acheteur peut ouvrir un litige tant que les fonds sont BLOCKED. Cela gèle automatiquement le délai de séquestre de 3 jours.

Méthode Route Accès Description
POST /api/payments/{id}/dispute/ Acheteur Déclaration d'un litige avec motif et détails.
GET /api/disputes/{id}/ Parties prenantes Consultation de l'état du litige.
POST /api/disputes/{id}/resolve/ Admin Arbitrage administratif (libération vers le vendeur ou remboursement de l'acheteur).

Module KYC (Know Your Customer)

Pour se conformer aux exigences réglementaires et sécuriser les échanges, les utilisateurs peuvent soumettre leur pièce d'identité (CNI, Passeport, Permis).

Méthode Route Accès Description
GET / POST /api/kyc/ Authentifié Consultation du statut ou soumission du dossier KYC.
POST /api/kyc/{id}/review/ Admin Validation (APPROVED) ou rejet motivé (REJECTED).
