Clés API pour 0xSeq

Permettre aux développeurs d'intégrer 0xSeq avec des clés secrètes révocables, limitées et stockées correctement.

Lire la version Markdown
Contexte 0xSeq. Le projet utilise déjà JWT avec l'en-tête Authorization: Bearer. Ce guide utilise donc X-API-Key pour éviter toute confusion entre les deux mécanismes.

1. Cycle de vie d'une clé

  1. Le développeur se connecte à 0xSeq.
  2. Il demande une clé et lui donne un nom, par exemple Application mobile.
  3. Le serveur génère un secret avec un générateur cryptographiquement sûr.
  4. Le serveur enregistre le propriétaire, le nom, les permissions et l'empreinte du secret, jamais le secret en clair.
  5. La clé complète est renvoyée une seule fois. Le développeur la conserve dans un gestionnaire de secrets.
  6. À chaque appel, le serveur retrouve la clé, vérifie son état et applique ses permissions.

Exemple de clé affichée une seule fois :

0xs_live_k3H...secret...

2. Modèle Django

Cette structure de départ associe chaque clé à son propriétaire, ses permissions et ses dates de cycle de vie.

import secrets

from django.conf import settings
from django.db import models


class APIKey(models.Model):
    user = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name="api_keys",
    )
    name = models.CharField(max_length=100)
    prefix = models.CharField(max_length=20, db_index=True)
    key_hash = models.CharField(max_length=64, unique=True)
    scopes = models.JSONField(default=list, blank=True)
    created_at = models.DateTimeField(auto_now_add=True)
    expires_at = models.DateTimeField(null=True, blank=True)
    revoked_at = models.DateTimeField(null=True, blank=True)
    last_used_at = models.DateTimeField(null=True, blank=True)

    @staticmethod
    def generate_secret():
        return "0xs_live_" + secrets.token_urlsafe(32)
  • user est le propriétaire de la clé.
  • name identifie l'intégration.
  • prefix aide à reconnaître la clé sans exposer le secret complet.
  • key_hash contient uniquement l'empreinte SHA-256.
  • scopes liste les actions permises, comme payments:read.
  • revoked_at non nul signifie que la clé a été révoquée.

Le modèle seul ne suffit pas : il faudra aussi implémenter la création, l'authentification, les permissions et les tests. Tout changement de modèle devra être suivi d'une migration Django.

3. Générer et stocker le secret

Python fournit le module secrets pour créer des valeurs imprévisibles. À la création, on peut enregistrer l'empreinte et renvoyer le secret complet une seule fois :

import hashlib

raw_key = APIKey.generate_secret()
key_hash = hashlib.sha256(raw_key.encode("utf-8")).hexdigest()

api_key = APIKey.objects.create(
    user=request.user,
    name=name,
    prefix=raw_key[:20],
    key_hash=key_hash,
    scopes=["payments:read"],
)

# Renvoyer raw_key au développeur une seule fois.

Une clé générée aléatoirement avec suffisamment d'entropie n'est pas un mot de passe humain : SHA-256 convient pour retrouver son empreinte. Il ne faut jamais journaliser ou réafficher le secret complet.

4. Envoyer une clé dans une requête

Une application cliente transmet sa clé dans un en-tête dédié :

GET /api/payments/
X-API-Key: 0xs_live_VOTRE_CLE

Le backend lit l'en-tête, calcule l'empreinte, recherche la clé, vérifie qu'elle n'est ni révoquée ni expirée, contrôle le scope et le droit d'accès à la ressource, puis autorise ou refuse la requête.

Dans ce projet, JWT est déjà configuré sur Authorization: Bearer. Une classe d'authentification personnalisée pourrait distinguer les clés 0xs_live_... des JWT si elles partageaient cet en-tête. X-API-Key évite cette ambiguïté.

5. Clés, scopes et paiements

Une clé reçoit uniquement les permissions nécessaires :

  • payments:read : consulter les paiements autorisés;
  • payments:create : créer une demande de paiement;
  • payments:refund : demander un remboursement, si les règles métier l'autorisent.

Une clé en lecture seule ne doit pas pouvoir créer un paiement ni libérer des fonds. Même avec un scope valide, le serveur doit vérifier que le propriétaire de la clé peut accéder au paiement. Une clé API identifie une intégration; elle ne remplace ni la propriété ni les permissions métier.

Pour 0xSeq, il faudra définir quel compte est associé à une clé et à quel titre il peut initier un paiement. Une requête authentifiée n'a pas automatiquement le droit d'agir comme acheteur ou vendeur.

6. Gestion et sécurité

  • Créer et nommer plusieurs clés.
  • Afficher le secret complet une seule fois.
  • Révoquer immédiatement une clé.
  • Limiter chaque clé à des scopes nécessaires.
  • Configurer une date d'expiration.
  • Suivre la dernière utilisation.
  • Limiter le débit et journaliser sans secret.
  • Empêcher un utilisateur de gérer les clés d'un autre.

En production, toutes les requêtes doivent passer par HTTPS. Le secret ne doit jamais être stocké dans le code source, envoyé dans une URL ou écrit dans les journaux.

7. Architecture conseillée pour 0xSeq

Le besoin décrit ici est de permettre aux développeurs d'intégrer l'API de 0xSeq. 0xSeq crée et gère donc les clés des intégrations de ses utilisateurs.

C'est différent d'une plateforme où les développeurs utiliseraient 0xSeq pour créer et gérer des clés destinées à leurs propres projets. Cette seconde architecture ferait de 0xSeq un service de gestion de clés.

  • User représente le compte et le propriétaire.
  • APIKey authentifie une intégration et porte ses scopes.
  • Paiement représente l'opération financière et conserve ses règles d'accès et de transition d'état.

8. Ordre d'implémentation

  1. Ajouter le modèle APIKey.
  2. Créer puis appliquer la migration.
  3. Créer une API qui affiche le secret une seule fois.
  4. Ajouter une classe d'authentification DRF pour X-API-Key.
  5. Vérifier les scopes et le propriétaire des paiements dans les permissions.
  6. Ajouter la révocation, l'expiration, les tests et la limitation du débit.

Teste cette fonctionnalité avant de protéger des opérations financières réelles. Une clé API ne déplace pas d'argent et ne doit jamais contourner les autorisations du modèle Paiement.
