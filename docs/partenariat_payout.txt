1. OBJECTIF ET PRINCIPE
================================================================================

Aujourd'hui, 0xSeq libère les fonds vers un portefeuille interne, puis le
vendeur demande un retrait Wave / Orange Money / MTN MoMo. Le virement
externe est confirmé manuellement par un administrateur.

Objectif du partenariat :

  - l'argent des acheteurs ne transite plus par 0xSeq ;
  - il est collecté et conservé par un prestataire agréé ;
  - 0xSeq donne l'instruction de payer le vendeur après livraison ;
  - le prestataire exécute le décaissement et confirme par webhook.

Principe directeur :

  "0xSeq ne détient jamais les fonds. 0xSeq orchestre la commande,
   le prestataire agréé détient et déplace l'argent."

Cette séparation est ce qui rend le montage défendable.

3. LES TROIS MODÈLES POSSIBLES
================================================================================

MODÈLE A — Compte marchand EME / PSP  (le plus simple)
-------------------------------------------------------
Qui détient les fonds : l'émetteur de monnaie électronique ou le PSP.
Fonctionnement :
  - les acheteurs paient sur le compte marchand du prestataire ;
  - 0xSeq suit la commande dans sa base ;
  - après livraison, 0xSeq demande un payout vers le vendeur ;
  - le prestataire paie et renvoie un webhook.

Avantages  : rapide, peu de conformité directe, une seule intégration.
Inconvénients : le prestataire est seul dépositaire ; vérifier la séparation
                des fonds et la protection en cas de faillite.

MODÈLE B — Marketplace / sous-marchands
----------------------------------------
Qui détient les fonds : le PSP, avec un compte ou un identifiant par vendeur.
Fonctionnement :
  - chaque vendeur est onboardé et vérifié (KYC) chez le PSP ;
  - la collecte est rattachée au vendeur ;
  - 0xSeq déclenche le payout depuis la plateforme.

Avantages  : plus propre pour une marketplace ; traçabilité par vendeur.
Inconvénients : onboarding plus lourd ; le PSP doit supported le "split"
                ou les "sub-merchants".

MODÈLE C — Compte séquestre bancaire + PSP technique
-----------------------------------------------------
Qui détient les fonds : une banque, sur un compte de cantonnement/séquestre.
Fonctionnement :
  - la banque ouvre un compte dédié aux fonds clients ;
  - le PSP exécute les collectes et les décaissements ;
  - 0xSeq instruit les mouvements.

Avantages  : protection et lisibilité maximales.
Inconvénients : coût, délais, montage contractuel lourd. Rarement adapté à
                un lancement solo.

RECOMMANDATION POUR UN FONDATEUR SOLO
--------------------------------------
Commencer par le MODÈLE A avec un agrégateur qui couvre Wave + Orange + MTN,
et vérifier contractuellement la séparation des fonds. Passer au modèle B
ensuite si le volume de vendeurs le justifie.

4. QUI PEUT ÊTRE QUALIFIÉ DE "PRESTATAIRE AGRÉÉ"
================================================================================

Trois familles à distinguer :

A. ÉMETTEURS DE MONNAIE ÉLECTRONIQUE (EME) / OPÉRATEURS
   Exemples de marché : Wave, Orange Money, MTN MoMo, Moov Money.
   Ce sont eux qui peuvent détenir de la monnaie électronique.
   À vérifier : agrément BCEAO, pays couverts, offre marchand/marketplace.

B. ÉTABLISSEMENTS DE PAIEMENT / AGRÉGATEURS
   Exemples : CinetPay, PayDunya, Hub2, Kkiapay, FedaPay.
   Ils agrègent plusieurs opérateurs.
   ATTENTION : un agrégateur n'est pas forcément le dépositaire des fonds.
   Demander explicitement : "qui détient l'argent et sous quel agrément ?"

C. BANQUES
   Nécessaires pour un vrai compte de cantonnement / séquestre.

RÈGLE DE BASE
-------------
Ne jamais se contenter de la page marketing. Demander :
  - le numéro d'agrément ;
  - le périmètre autorisé ;
  - la confirmation écrite du dépositaire ;
  - la liste officielle BCEAO correspondante.

9. FLUX TECHNIQUE CIBLE
================================================================================

   Acheteur
      |
      | 1. Checkout
      v
   Prestataire agréé  <---------- 0xSeq (création de la commande)
      |                              |
      | 2. Fonds encaissés           | 3. Webhook "fonds reçus"
      |    et conservés              |    -> Paiement BLOCKED
      |                              |
      |                              | 4. Livraison confirmée
      |                              |    -> instruction de payout
      | 5. Payout vers le vendeur    |
      |    Wave / Orange / MTN       |
      |                              |
      | 6. Webhook payout.completed  |
      |    ou payout.failed          |
      v                              v
   Vendeur                      0xSeq met à jour le statut
                                et la réconciliation

POINTS CLÉS
  - 0xSeq ne stocke jamais l'argent.
  - Le solde "wallet" interne devient un miroir des fonds chez le prestataire
    ou disparaît au profit d'un solde prestataire.
  - Toute instruction de payout doit être idempotente.
  - Chaque payout doit avoir une référence interne unique.

================================================================================

Vous êtes seul : l'objectif est de réduire le nombre d'intégrations et de
négociations. Un seul agrégateur multi-opérateurs vaut mieux que trois
intégrations Wave + Orange + MTN séparées.

SEMAINE 1 — CADRAGE
  [ ] Relire ce document.
  [ ] Consulter la liste officielle BCEAO des EME / établissements agréés.
  [ ] Présélectionner 4 à 6 prestataires.
  [ ] Envoyer l'e-mail type (section 13) à chacun.

  [ ] Vérifier les agréments.
  [ ] Poser les questions techniques (section 7).
  [ ] Demander la documentation API et l'accès sandbox.
  [ ] Éliminer ceux qui ne peuvent pas prouver le dépositaire des fonds.

SEMAINE 3 — SÉLECTION
  [ ] Comparer sur : agrément, couverture, payout API, tarifs, délais.
  [ ] Choisir un prestataire principal et un plan B.
  [ ] Constituer le dossier KYB (section 6).

  [ ] Faire relire le contrat par un juriste.

  [ ] Obtenir les clés sandbox.

SEMAINES 7 À 10 — INTÉGRATION

12. EN ATTENDANT : MODE MANUEL RENFORCÉ
================================================================================

Le circuit actuel est déjà fonctionnel. Pour limiter les risques :

  [ ] KYC vendeur obligatoire avant tout retrait.
  [ ] Plafond de retrait par jour et par vendeur.
  [ ] Double validation : un admin prépare, un second confirme.
      (Si vous êtes seul, imposer au moins un délai de réflexion et une
       vérification téléphonique du bénéficiaire.)
  [ ] Référence de transfert obligatoire avant de marquer COMPLETED.
  [ ] Preuve de virement archivée (capture, reçu opérateur).
  [ ] Vérification du numéro bénéficiaire (nom + téléphone).
  [ ] Journal d'audit : qui a validé, quand, quel montant.
  [ ] Réconciliation quotidienne entre les soldes internes et les comptes
      Mobile Money.
  [ ] Alerte si un vendeur demande un retrait juste après une libération.
  [ ] Ne jamais marquer COMPLETED sans transfert réel effectué.

RAPPEL
------
Le solde du portefeuille interne est une dette de la plateforme envers le
vendeur. Il doit toujours être couvert par des fonds réellement encaissés.

15. POINTS DE VIGILANCE JURIDIQUE
================================================================================

  - Ne pas se présenter comme "séquestre agréé" ou "établissement de paiement"
    sans agrément.
  - Utiliser une formulation honnête : "paiement sécurisé avec libération
    après livraison", "fonds conservés par un partenaire agréé".
  - Vérifier qui, juridiquement, détient les fonds.
  - Vérifier la séparation des fonds clients.
  - Vérifier les obligations KYC/AML et qui les porte.
  - Vérifier la protection des données personnelles.
  - Faire relire le contrat par un avocat spécialisé UEMOA/BCEAO.
  - Conserver toutes les preuves d'agrément et les échanges écrits.
  - Ne pas promettre aux vendeurs un décaissement instantané avant que le
    prestataire ne le garantisse contractuellement.

16. LEXIQUE
================================================================================

BCEAO      Banque Centrale des États de l'Afrique de l'Ouest.
EME        Émetteur de Monnaie Électronique (peut détenir de la monnaie
           électronique).
PSP        Prestataire de services de paiement.
EP         Établissement de paiement.
KYC        Know Your Customer — vérification de l'identité.
KYB        Know Your Business — vérification de l'entreprise.
AML/CFT    Anti-Money Laundering / Combating the Financing of Terrorism.
Payout     Décaissement vers un bénéficiaire (vendeur).
Disbursement  Synonyme de payout.
Split payment  Répartition automatique d'un paiement entre plusieurs acteurs.
Cantonnement  Séparation des fonds clients des fonds propres.
Cut-off    Heure limite de prise en charge d'un virement pour le jour ouvré.
SLA        Engagement de niveau de service.
Idempotence  Propriété qui empêche qu'une même instruction soit exécutée
             deux fois.
XOF        Franc CFA UEMOA.

================================================================================
18. PSP, P2P ET NON-DÉTENTION DES FONDS
================================================================================

18.1 QU'EST-CE QU'UN PSP ?
--------------------------
PSP = Prestataire de Services de Paiement.

C'est une entreprise autorisée à fournir des services de paiement :
encaisser, transférer, ouvrir des comptes de paiement, exécuter des
décaissements. C'est un statut réglementaire défini par la BCEAO.

  PSP      = statut légal : autorisé à faire transiter des paiements.
  EME      = sous-catégorie de PSP : peut émettre et détenir de la monnaie
             électronique (Wave, Orange Money, MTN MoMo...).
  Agrégateur = rôle technique/commercial : connecte plusieurs opérateurs via
             une API (CinetPay, PayDunya...). Pas forcément PSP lui-même.
  Banque   = peut porter un compte de cantonnement/séquestre.

Attention : beaucoup de fintechs se disent "PSP" commercialement sans avoir
l'agrément. Vérifier par un numéro d'agrément BCEAO et un périmètre précis.

18.2 SUIS-JE OBLIGÉ D'AVOIR UN PSP ?
------------------------------------
La question centrale n'est pas "suis-je P2P ?" mais :

  "Est-ce que l'argent des acheteurs passe un jour sur un compte que je
   contrôle ?"

  Cas A. L'argent va directement chez le vendeur (son compte Wave/OM/MTN).
         -> 0xSeq ne détient rien : pas besoin d'être PSP.

  Cas B. L'argent va chez un PSP agréé, sur un compte sous-marchand du
         vendeur ; le PSP paie le vendeur sur instruction.
         -> 0xSeq ne détient rien : pas besoin d'être PSP.

  Cas C. L'argent est encaissé sur le compte marchand de 0xSeq, conservé
         par 0xSeq, puis reversé plus tard.
         -> 0xSeq détient des fonds pour compte de tiers : agrément EME/PSP
            ou partenaire agréé nécessaire.

SITUATION ACTUELLE DE 0xSEQ
---------------------------
Les paiements arrivent sur le compte marchand GeniusPay de 0xSeq, puis sont
crédités dans un wallet interne. 0xSeq est donc dans le cas C, même si
GeniusPay est un fournisseur technique agréé.

Conséquence : le mot "séquestre" est juridiquement fragile tant que 0xSeq
contrôle les fonds. Il faut soit un partenaire qui les détient, soit changer
le flux.

18.3 MON CODE ACTUEL EST-IL P2P ?
---------------------------------
NON. Le code actuel est un marketplace avec séquestre et portefeuille
interne, pas un P2P.

  initiate_payment()  -> l'argent arrive sur le compte marchand 0xSeq
  Paiement            -> commande encadrée par la plateforme
  release_funds()     -> crédite une dette interne (wallet vendeur)
  WalletTransaction   -> la plateforme doit l'argent au vendeur
  retrait admin       -> la plateforme exécute le décaissement

Un vrai P2P serait :

  Acheteur -> paiement direct -> Vendeur
  0xSeq ne touche jamais l'argent (matching, lien, suivi, commission).

"P2P" n'est pas un statut juridique protecteur. Ce qui compte, c'est qui
contrôle l'argent. Un P2P qui conserve ou contrôle les fonds peut être
requalifié en service de paiement.

18.4 COMMENT NE PAS DÉTENIR LES FONDS (MODÈLE RECOMMANDÉ)
---------------------------------------------------------
Objectif : 0xSeq ne reçoit jamais l'argent.

Conditions à remplir :
  [ ] Aucun compte bancaire 0xSeq ne reçoit les paiements acheteurs.
  [ ] Aucun compte marchand 0xSeq (GeniusPay ou autre) ne les reçoit.
  [ ] Aucun wallet interne ne représente une dette de 0xSeq envers le vendeur.

Modèle B — compte sous-marchand PSP :

  Acheteur -> PSP -> compte sous-marchand du vendeur (chez le PSP)
                          |
                   0xSeq suit la commande
                          |
                   livraison confirmée
                          |
           0xSeq -> PSP : libère / paie le vendeur
                          |
                   PSP -> Wave / OM / MTN

Étapes :
  1. Choisir un PSP avec comptes sous-marchands, split payment ou delayed
     capture, API de payout et webhooks signés.
  2. Onboarder chaque vendeur chez le PSP (KYC fait par le PSP).
     Stocker son identifiant : provider_account_id.
  3. Créer le checkout sur le compte du vendeur, avec les métadonnées de
     commande. L'argent ne passe pas par 0xSeq.
  4. À la livraison, appeler l'API de capture/payout du PSP. La commission
     0xSeq est prélevée par split ou facturée séparément.
  5. Réconcilier via webhooks payout.completed / payout.failed et un contrôle
     quotidien solde PSP vs commandes locales.

18.5 MODÈLE A — PAIEMENT DIRECT AU VENDEUR (FALLBACK)
-----------------------------------------------------
L'acheteur paie directement le vendeur (son propre compte marchand ou
wallet). 0xSeq ne fait que générer le lien, suivre la commande et confirmer
la livraison.

Avantage  : simplicité, aucune détention.
Inconvénient : plus de séquestre réel ; le vendeur est payé avant livraison.
Mitigations possibles : vendeurs vérifiés, plafonds, paiement à la livraison,
garantie vendeur, assurance, historique de confiance.

18.6 CE QU'IL FAUT CHANGER DANS LE CODE
---------------------------------------
  [ ] Ajouter provider_account_id sur le vendeur (compte PSP).
  [ ] Créer un modèle Payout (statuts, référence, idempotency_key).
  [ ] Créer une interface PayoutProvider + adaptateur PSP.
  [ ] Remplacer le crédit wallet par un appel payout au PSP.
  [ ] Garder un mode manual en secours (feature flag).
  [ ] Le wallet devient un miroir du solde PSP, ou disparaît.
  [ ] Ajouter la réconciliation PSP et les alertes.
  [ ] Mettre à jour les CGU.

Tableau avant / après :

  Aujourd'hui                         Demain (sans détention)
  ----------------------------------  --------------------------------------
  Compte marchand 0xSeq               Comptes sous-marchands vendeurs
  escrow_credits = dette interne      Solde miroir du PSP
  release_funds() crédite le wallet   release_funds() appelle le PSP
  Wallet = engagement de 0xSeq        Wallet = affichage solde PSP (ou rien)
  Retrait validé par admin            Payout exécuté par le PSP

18.7 FORMULATIONS CGU
---------------------
Honnête (si modèle B) :
  "Les paiements sont collectés et conservés par [PSP], établissement agréé.
   0xSeq fournit le service de coordination de la commande et de la livraison
   et n'agit pas comme dépositaire des fonds."

À éviter tant que ce n'est pas vrai :
  "Vos fonds sont séquestrés et garantis par 0xSeq."
  "0xSeq est un séquestre agréé."

18.8 DÉCISION RECOMMANDÉE POUR UN FONDATEUR SOLO
------------------------------------------------
  1. Ne pas demander un agrément EME/PSP maintenant.
  2. Choisir un PSP/EME avec comptes sous-marchands et payout.
  3. Faire vérifier le montage par un avocat UEMOA avant communication.
  4. En attendant : mode manuel, plafonds, KYC vendeurs, preuves de virement.
  5. Ne pas encaisser de nouvelles ventes de tiers sur le compte marchand
     0xSeq si le modèle cible est la non-détention.
